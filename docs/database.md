# Database — PeptoLogics

Supabase PostgreSQL. Project ref `pmbatptoffscqtnfmhbz`.

Design rationale: ADR-001 to ADR-004 and ADR-011 in [decisions.md](./decisions.md).

---

## Conventions

- `snake_case` for tables and columns. Never camelCase.
- UUID primary keys via `gen_random_uuid()` — core Postgres since 13, so no `pgcrypto`.
- `created_at` and `updated_at timestamptz not null default now()` on every table, UTC, generated by
  the database. `updated_at` is stamped by a trigger so a client cannot forge it.
- `deleted_at timestamptz` for soft deletes on business data.
- Money as `integer` cents, columns suffixed `_cents` (ADR-002).
- Controlled vocabularies as `text` + `CHECK` rather than a Postgres `enum` — adding a value to an
  enum is a migration that cannot run inside a transaction alongside other DDL.
- No `SELECT *`. Repositories name their columns explicitly.

## Entity relationships

```
products ─────┐
              ├──< order_items >──── orders ────< notification_log
  (RESTRICT)  │        (CASCADE)                     (CASCADE)

rate_limit_hits          (standalone — no relationships)
```

`order_items.product_id` is `ON DELETE RESTRICT`: a product that appears on a historical inquiry must
not be deletable. Retire it with `status = 'archived'` instead.

## `products`

The catalog. 12 rows seeded.

| Column                                   | Type            | Notes                                                                                          |
| ---------------------------------------- | --------------- | ---------------------------------------------------------------------------------------------- |
| `id`                                     | `uuid` PK       | `gen_random_uuid()`                                                                            |
| `slug`                                   | `text` UNIQUE   | `CHECK` enforces `^[a-z0-9]+(-[a-z0-9]+)*$`                                                    |
| `name`                                   | `text`          | 1–200 chars after trim                                                                         |
| `description`                            | `text` NULL     | **NULL for all 12.** Client-supplied copy — see open question 1                                |
| `category`                               | `text`          | `peptide` \| `blend` \| `cosmetic` \| `supply` — **PLACEHOLDER vocabulary**                    |
| `strength_mg`                            | `numeric(10,3)` | Milligrams per vial. Numeric so a sub-mg product needs no migration                            |
| `price_cents`                            | `integer`       | `> 0`                                                                                          |
| `cost_per_mg`                            | `numeric(10,4)` | **GENERATED STORED**, `price_cents / 100 / strength_mg`. Read-only — writing it raises `428C9` |
| `is_blend`                               | `boolean`       | Suppresses cost-per-mg display; the figure is not comparable for a blend                       |
| `featured`                               | `boolean`       | Home page strip                                                                                |
| `sort_order`                             | `integer`       | `>= 0`. Display order                                                                          |
| `image_url`, `coa_url`                   | `text` NULL     | Unpopulated. No product photography exists                                                     |
| `status`                                 | `text`          | `active` \| `out_of_stock` \| `archived`                                                       |
| `created_at`, `updated_at`, `deleted_at` | `timestamptz`   |                                                                                                |

Indexes: `(status, sort_order, name) WHERE deleted_at IS NULL` · `(sort_order) WHERE featured AND
status='active'` · `(cost_per_mg) WHERE status='active'` · unique on `slug`.

The generated column reproduces the client's price list exactly — verified against all 12 rows:
`6.00, 5.00, 8.00, 0.60, 6.00, 5.00, 0.03, 6.00, 0.11, 1.13, 3.33, 4.50`. Values are stored at full
precision and rounded only for display: K-L-O-W's true value is `1.125` and Glutathione's is
`0.0333`.

**Corrected 8 August 2026** on the client's instruction: Tesamorelin 10 mg → 5 mg at $40,
Glutathione 10 mg → 1500 mg at $50, MOTS-c $50 → $60, K-L-O-W $75 → $90 with `is_blend` cleared so
its cost-per-mg is shown. The two size changes renamed their slugs, so `next.config.ts` carries a
permanent redirect for each old URL.

## `orders`

Customer inquiries. **Not purchases** — no payment is processed. `subtotal_cents` is indicative.

| Column                                 | Type               | Notes                                                                                                                                                     |
| -------------------------------------- | ------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                   | `uuid` PK          |                                                                                                                                                           |
| `order_number`                         | `text` UNIQUE      | `'PL-' \|\| lpad(nextval(...), 6, '0')` from `order_number_seq`, starting at 1000. Sequence gaps are normal — a rolled-back insert still consumes a value |
| `idempotency_key`                      | `uuid` UNIQUE      | The whole duplicate-submission defence                                                                                                                    |
| `customer_name`, `email`, `phone`      | `text`             | All required                                                                                                                                              |
| `address`, `city`, `state`, `zip_code` | `text`             | All required                                                                                                                                              |
| `apartment`, `notes`                   | `text` NULL        | The only optional fields. Whitespace-only input is coerced to NULL by `create_inquiry`                                                                    |
| `country`                              | `char(2)`          | Defaults `'US'` — **PLACEHOLDER**, geography unconfirmed                                                                                                  |
| `subtotal_cents`                       | `integer`          | Computed server-side from `products.price_cents`, never from the payload                                                                                  |
| `currency`                             | `char(3)`          | Defaults `'USD'`                                                                                                                                          |
| `item_count`                           | `integer`          | `> 0`                                                                                                                                                     |
| `status`                               | `text`             | `new` \| `contacted` \| `confirmed` \| `cancelled` \| `completed`                                                                                         |
| `ruo_acknowledged_at`                  | `timestamptz` NULL | When the visitor accepted the gate                                                                                                                        |

Length `CHECK`s on every text field, plus a deliberately permissive email-shape check. Real validation
is the Zod schema; these constraints exist to stop obviously malformed data reaching storage, not to
implement RFC 5322.

Indexes: `(created_at desc)` · `(status, created_at desc)` · `(email)` — all `WHERE deleted_at IS NULL`.

## `order_items`

One row per product line. Rows, not a JSON blob, so lines can be aggregated, constrained and joined.

`product_name`, `product_slug` and `strength_mg` are **point-in-time snapshots**: a later rename or
repricing must not rewrite history, and the follow-up call needs to show what the customer saw.

Key constraints:

- `UNIQUE (order_id, product_id)` — quantity lives on one row, so a product cannot appear twice.
- `CHECK (subtotal_cents = unit_price_cents * quantity)` — the invariant integer cents exist to make
  possible. Any drift between a line total and its parts is rejected at the storage layer.
- `CHECK (quantity BETWEEN 1 AND 99)` — **PLACEHOLDER** upper bound.

## `notification_log`

One row per order per channel. This table is what makes notification failure survivable: the order
commits first, `create_inquiry` writes a `pending` row per channel, and the notification service
updates it afterwards. Nothing can throw back into the order transaction.

`status` is `pending` \| `sent` \| `failed` \| `skipped`. **`skipped` is a first-class outcome**, not an
error — it is what a channel with no credentials configured records. Keeping it distinct from `failed`
is what makes the dead-letter list meaningful before Resend and Meta are set up.

The partial index `(created_at desc) WHERE status IN ('pending','failed')` **is** the dead-letter
list: an operator can see exactly which leads were never delivered, and it stays tiny regardless of
table size.

## `rate_limit_hits`

Fixed-window abuse counters. `bucket_key` is a **salted SHA-256 of the client IP**, hashed in Node
before it reaches the database (`src/lib/security/request.ts`). The counter needs a stable key, not an
identity, so a raw address would be PII held for no reason.

`UNIQUE (bucket_key, window_started_at)` is what makes the counter atomic — concurrent callers
collide on the index and increment rather than racing.

## Functions

| Function                         | Security                  | Purpose                                                                             |
| -------------------------------- | ------------------------- | ----------------------------------------------------------------------------------- |
| `set_updated_at()`               | invoker, `search_path=''` | Trigger helper. Not business logic                                                  |
| `create_inquiry(jsonb)`          | invoker, `search_path=''` | Atomically inserts one order + N items + one `pending` notification row per channel |
| `check_rate_limit(text,int,int)` | invoker, `search_path=''` | Atomic increment-and-test                                                           |

All three pin `search_path` so they cannot be hijacked by a caller with a crafted path. `pg_catalog`
remains implicitly searchable, so built-ins still resolve; only `public` objects are qualified.

### `create_inquiry` — the atomicity guarantee

The Supabase JS client cannot express a multi-statement transaction over PostgREST, so inserting an
order then its items is not atomic from application code. A compensating delete on failure was
rejected: that is a distributed-transaction pattern which can itself fail, leaving exactly the
orphaned state it was meant to prevent.

Returns `{ order_id, order_number, created }`. On a duplicate `idempotency_key` the insert does
`ON CONFLICT DO NOTHING`, the original order is read back, and `created` is `false` — which is how the
service knows to skip notifications on a replay.

Verified: two calls with the same key produced one order (`PL-001000`), `created: true` then `false`,
one `order_items` row, two `notification_log` rows both `pending`.

### `check_rate_limit`

One statement does the whole job. Reading the counter then updating it from application code would be
a race — two concurrent requests could both read 5 and both allow. `INSERT ... ON CONFLICT DO UPDATE
... RETURNING` increments and reports the post-increment value atomically.

Returns `{ allowed, hit_count, limit, retry_after_seconds }`. Verified sequentially: hits 1–5 allowed,
hit 6 blocked, with a valid `Retry-After`.

> Note when testing: calling either function repeatedly in a single `SELECT` gives misleading results
> — the planner hoists the call and evaluates it once. Test in a loop, or across separate statements.

## Privileges and RLS

RLS is enabled on all five tables. **RLS alone does not describe what a role can do** — a policy can
only narrow access that a `GRANT` already permits, and some privileges ignore RLS entirely. Both
layers were probed against the live database.

|                          | `products`                                                               | `orders`                 | `order_items`    | `notification_log`       | `rate_limit_hits`                |
| ------------------------ | ------------------------------------------------------------------------ | ------------------------ | ---------------- | ------------------------ | -------------------------------- |
| `anon` / `authenticated` | `SELECT`, narrowed by policy to `status='active' AND deleted_at IS NULL` | —                        | —                | —                        | —                                |
| `service_role`           | `SELECT`                                                                 | `SELECT, INSERT, UPDATE` | `SELECT, INSERT` | `SELECT, INSERT, UPDATE` | `SELECT, INSERT, UPDATE, DELETE` |

`EXECUTE` on `create_inquiry` and `check_rate_limit` is revoked from `PUBLIC`, `anon` and
`authenticated`; granted only to `service_role`.

### Two problems found by probing, both fixed

**1. `anon` had no `SELECT` on `products`.** Supabase's default privileges on this project grant only
`REFERENCES, TRIGGER, TRUNCATE` on new public tables, and no DML to anyone. So `products_public_read`
was dead weight and the catalog read path would have failed outright with _permission denied for table
products_. Fixed in `20260806100800_grants.sql`.

**2. `anon` held `TRUNCATE` on every table, including `orders`.** `TRUNCATE` is **not filtered by row
level security**. A leaked anon key plus any path executing SQL as anon could have run
`truncate public.orders cascade` and destroyed every lead, line item and delivery record — despite
`orders` having RLS enabled with no policies. `TRUNCATE`, `TRIGGER` and `REFERENCES` are now revoked
from `anon`, `authenticated` **and** `service_role`, and `ALTER DEFAULT PRIVILEGES` is adjusted so a
future migration does not silently reintroduce them.

**3. `service_role` had no DML at all** (same root cause as 1). `BYPASSRLS` exempts a role from row
level security but does not grant table privileges — only one of the two was present, so the inquiry
write path would have failed on the first real submission. Fixed in
`20260806100900_service_role_grants.sql`, granted per table at the narrowest privilege each code path
needs rather than a blanket `GRANT ALL`.

**4. A pre-existing function, `public.rls_auto_enable()`**, backs the `ensure_rls` event trigger that
auto-enables RLS on new public tables. It is `SECURITY DEFINER` owned by `postgres` and `EXECUTE` was
held by `PUBLIC`, so `anon` could invoke it over `/rest/v1/rpc/rls_auto_enable` and it would run with
postgres privileges. Confirmed reachable by direct test. Current impact is nil — outside an
event-trigger context `pg_event_trigger_ddl_commands()` yields no rows — but it is a standing
privilege-escalation surface on the public API. `EXECUTE` is revoked in
`20260806101000_harden_rls_auto_enable.sql`; the event trigger still fires, verified by creating a
table and confirming RLS was switched on automatically.

### The four `rls_enabled_no_policy` advisor notices are intentional

`orders`, `order_items`, `notification_log` and `rate_limit_hits` have RLS enabled with **no
policies**, which denies everything to `anon` and `authenticated`. That is the design: customer PII
must not be readable with any key that could reach a browser. The Supabase linter reports this at INFO
level; it is not a defect. `get_advisors` is otherwise clean.

## Migration workflow

Schema changes are version-controlled and applied through migrations only — never by hand-editing a
database.

```bash
npm run db:new <descriptive_name>
# write the SQL, then apply locally
npm run db:reset
npm run db:types
```

Applied to the linked project with `npm run db:push`, or via the Supabase MCP `apply_migration`.

Files under `supabase/migrations/`, in order:

| File                                 | Contents                                                            |
| ------------------------------------ | ------------------------------------------------------------------- |
| `…100000_helpers.sql`                | `set_updated_at()`                                                  |
| `…100100_products.sql`               | `products` + generated column, indexes, RLS policy                  |
| `…100200_orders.sql`                 | `order_number_seq`, `orders`, indexes, RLS                          |
| `…100300_order_items.sql`            | `order_items`, FKs, arithmetic invariant, RLS                       |

## Seed data

`supabase/seed.sql` holds the 12 products as idempotent upserts keyed on `slug`, so re-running it is
safe and a price correction is an edit plus a re-run. `description` is `NULL` on every row by design.

## Generated types

`src/types/database.types.ts`, regenerated with `npm run db:types`. Two runtime caveats the generator
cannot express, both handled once in `src/features/products/mappers/product.mappers.ts`:

1. `cost_per_mg` and `strength_mg` are typed `number` but PostgREST serialises `numeric` as a JSON
   **string** to avoid IEEE-754 loss — they arrive as `"6.0000"` and `"10.000"`.
2. `cost_per_mg` appears in `Insert`/`Update` but writing it raises `428C9`.
