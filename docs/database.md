# Database — PeptoLogics

Supabase PostgreSQL. Project ref `pmbatptoffscqtnfmhbz`.

> **Status: skeleton.** Filled in during Phase 1, when the migrations are written and applied.
> Design rationale already recorded: ADR-001 through ADR-004 and ADR-011 in [decisions.md](./decisions.md).

---

## Conventions

- `snake_case` for tables and columns. Never camelCase.
- UUID primary keys via `gen_random_uuid()` (`pgcrypto`).
- `created_at` and `updated_at timestamptz not null default now()` on every table, UTC, generated by
  the database — never by a client.
- `deleted_at timestamptz` for soft deletes on business data.
- Money as `integer` cents, columns suffixed `_cents` (ADR-002).
- Controlled vocabularies as `text` with a `CHECK` constraint rather than a Postgres `enum` — adding a
  value to an enum requires a migration that cannot run inside a transaction with other DDL.
- No `SELECT *`. Repositories name their columns explicitly.

## Tables

| Table              | Purpose                                                              |
| ------------------ | -------------------------------------------------------------------- |
| `products`         | The catalog. 12 rows at launch.                                      |
| `orders`           | Customer inquiries. One row per submission.                          |
| `order_items`      | One row per product line on an inquiry.                              |
| `notification_log` | One row per order per channel. Delivery record and dead-letter list. |
| `rate_limit_hits`  | Fixed-window abuse counters, keyed on a hashed IP.                   |

Relationships:

```
products ──┐
           ├──< order_items >── orders ──< notification_log
           │
    (RESTRICT)          (CASCADE)
```

`order_items.product_id` is `ON DELETE RESTRICT` — a product that appears on a historical inquiry
must not be deletable. `order_items.order_id` is `ON DELETE CASCADE`.

## Functions

| Function                             | Purpose                                                                                                                                            |
| ------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `set_updated_at()`                   | Trigger helper. Stamps `updated_at` on UPDATE. Not business logic.                                                                                 |
| `create_inquiry(payload jsonb)`      | The atomicity guarantee. Inserts one order plus N items in one transaction, `ON CONFLICT (idempotency_key) DO NOTHING`, then reads back. (ADR-004) |
| `check_rate_limit(key, max, window)` | Atomic increment-and-test. Returns whether the caller is over the limit and how long until the window resets. (ADR-011)                            |

## Row Level Security

RLS is enabled on every table. There is no authentication in scope, so the posture is:

| Role           | `products`                                                | `orders` / `order_items` / `notification_log` / `rate_limit_hits` |
| -------------- | --------------------------------------------------------- | ----------------------------------------------------------------- |
| `anon`         | `SELECT` where `status = 'active' AND deleted_at IS NULL` | nothing                                                           |
| `service_role` | full (bypasses RLS)                                       | full                                                              |

The browser never talks to Supabase. Reads use the anon key server-side so RLS acts as a second layer
behind the repository's own filters; writes use the service-role key, server-side only.

## Migration workflow

Schema changes are version-controlled and applied through migrations only — never by editing a
production database by hand.

```bash
npx supabase migration new <descriptive_name>
# write the SQL, then apply locally
npx supabase db reset
# regenerate types
npm run db:types
```

Production is applied via the Supabase MCP `apply_migration`, or `npx supabase db push` against the
linked project.

## Seed data

`supabase/seed.sql` holds the 12 products as idempotent upserts keyed on `slug`, so re-running it is
safe. Development seed data is kept separate from production data.
